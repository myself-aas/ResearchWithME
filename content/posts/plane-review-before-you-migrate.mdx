### Key findings
- The issue model captures workflow relationships, not just task text.
- The root Compose file exposes application, worker and stateful-service responsibilities.
- A project-local sequence lock is a narrow source observation, not proof of all-path concurrency correctness.

## Review question and scope

How much infrastructure and data-model commitment sits behind a self-hosted project tracker? This review is for engineering teams evaluating issue tracking, cycles and project migration. It examines [makeplane/plane](https://github.com/makeplane/plane) at commit `da21a8ff8b4b0a1d7bfcca72eb184a13233bb143`, a pinned **default-branch source snapshot, not a release tag**. Findings apply to that snapshot rather than every packaged or hosted edition.

## Bottom line: evaluate the workflow and the operator role

Plane is a candidate for teams seeking project tracking with control over deployment. Its README describes work items, cycles, modules, views, pages and analytics, and offers Cloud and self-hosting routes. This review treats those as product descriptions, not evidence that a migration will preserve every workflow or that self-hosting removes administration. [1](https://github.com/makeplane/plane/blob/da21a8ff8b4b0a1d7bfcca72eb184a13233bb143/README.md#L27-L167)

The most useful adoption question is whether the team wants both the application model and the responsibility for operating it. A tracker is not just a list of titles: state transitions, identifiers, relationships, attachments and access rules become part of everyday work. The selected model and deployment files make some of those commitments visible.

## The data model carries migration assumptions

The `Issue` model includes parent and state relationships, several description representations, priority, dates, assignees, labels and a sequence identifier. A default manager excludes triage, archived, archived-project and draft records in the inspected queryset. That is a meaningful warning against using one default query as a complete export without checking its scope. It is not evidence that Plane’s export tools are incomplete. [3](https://github.com/makeplane/plane/blob/da21a8ff8b4b0a1d7bfcca72eb184a13233bb143/apps/api/plane/db/models/issue.py#L91-L214)

The inspected creation path enters a database transaction and obtains a project-derived PostgreSQL advisory transaction lock before computing a sequence and saving related sequence data. This shows deliberate project-local coordination in that path. It does not prove behavior for bulk inserts, all APIs, contention levels or every race condition; the same file contains a TODO about bulk-insert identifiers. [3](https://github.com/makeplane/plane/blob/da21a8ff8b4b0a1d7bfcca72eb184a13233bb143/apps/api/plane/db/models/issue.py#L91-L214)

My migration recommendation is to compare source and destination counts by record type and status, not only by what appears in the ordinary work-item view. Verify historical identifiers, relationships and non-active records with representative fixtures before importing a real project.

## Self-hosting is a service lifecycle

The root Compose file defines frontend-facing services, an API, worker and beat-worker, a migrator and a live service. Its stateful definitions include PostgreSQL, a service named `plane-redis` using a Valkey image, RabbitMQ and object storage. ## Configuration is not a security verdict

Production settings derive `DEBUG` from an environment value and honor `X-Forwarded-Proto` for secure-request detection. Those lines are useful deployment inputs, not a full hardening checklist or proof of safe proxy configuration. No workspace authorization, public sharing, attachment access or session behavior was exercised. [4](https://github.com/makeplane/plane/blob/da21a8ff8b4b0a1d7bfcca72eb184a13233bb143/apps/api/plane/settings/production.py#L1-L15)

The project’s root terms are AGPL v3, including the modified-version network-interaction condition. Teams modifying or redistributing the application should review actual obligations; this review does not supply legal advice or an edition entitlement map. [5](https://github.com/makeplane/plane/blob/da21a8ff8b4b0a1d7bfcca72eb184a13233bb143/LICENSE.txt#L1-L550)

I would shortlist Plane when its work model matches the team’s process and an operator can own upgrades, restore and access verification. I would delay a replacement decision if the evaluation covers only attractive screenshots or the creation of one issue. No usability comparison, production deployment, import or concurrency test was performed here.

## What can a reader inspect or reproduce?

This is static source inspection, not a benchmark, production deployment, certification, or penetration test. No upstream package was installed, no upstream tests or security probes were run, and no runtime measurements were collected. Repository documentation reports intended behavior; code passages establish only the inspected mechanism. Adoption recommendations throughout are reviewer analysis, not measured outcomes.

For a next-stage evaluation:

1. Migrate a synthetic project containing archived, triage and draft items, parent links, assignees and attachments; reconcile counts and relationships.
2. Exercise concurrent issue creation and any bulk-import path without assuming one inspected lock covers every path.
3. Stage a version upgrade and a database-plus-upload restore; verify workspace and attachment permissions with separate test users.
