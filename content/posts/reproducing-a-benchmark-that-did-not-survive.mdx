A throughput claim can change meaning when warm-up, process lifetime, and baseline treatment are underspecified. This worked example uses an unverified benchmark scenario to explain that failure mode; its numerical examples are not established measurements. A defensible reproduction needs a public harness, matched workloads, raw runs, and explicit timing boundaries before any performance conclusion.

## The claim

The claim is simple enough to fit in a sentence: a hypothetical scheduler moves 2.4× more requests per second
than the baseline, at equal tail latency. The scenario assumes an evaluation reporting a single configuration —
batch size 64, one worker per core, 30-second runs — and a footnote says results are averaged over
five runs.

Even those assumed settings are not enough to reproduce a result without the workload, environment and timing contract.

## What would need to be run?

The earlier draft claimed a local reproduction, but no named paper, public harness, environment record or raw output accompanies it. The commands below are **illustrative** and refer to an unavailable `bench/serve.py`; they are not runnable evidence or a recipe for an identified upstream system.

```bash
# Published configuration: warm process, 30 s window, five repetitions.
python bench/serve.py --batch-size 64 --workers 8 --duration 30 --reps 5

# Cold start: a fresh process per measurement, no warm-up window.
for i in $(seq 1 5); do
  python bench/serve.py --batch-size 64 --workers 8 --duration 30 --reps 1
done
```

## Which choices could reverse the ranking?

Three choices could produce such a gap. None is established for an actual paper here:

1. **Warm-up is excluded from the measurement.** Standard practice for serving benchmarks, and
   invisible unless you read the harness.
2. **Only one process lifetime is measured.** The harness starts a single server and loops requests
   against it, so cold start never appears in the data.
3. **The baseline is not given the same warm-up.** This one is harder to defend — the comparison
   numbers come from a baseline that starts cold in every repetition.

The third point is the one I would raise in review. The first two are documentation failures; the
third is a comparison that favours the proposed system by construction.

## Why this matters beyond one paper

Framing reproduction only as “the number matched” or “it did not” can hide a measurement-contract
mismatch. In this scenario, the missing timing boundary is the issue to investigate. In a real
reproduction, implementation bugs, workload differences and ordinary variation are alternative
explanations; the scenario does not establish how often any of them occurs.

<Callout tone="note" title="A reporting checklist that would have caught this">
  For every throughput claim, publish (a) process lifetime, (b) whether warm-up is inside the
  measurement window, (c) the exact command that produces each row, and (d) the same information for
  the baseline. Those details are necessary starting points; they do not guarantee a reproduction deadline.
</Callout>

## What I would change

If a result depends on a warm process, state that scope alongside the headline. “2.4× at steady
state” identifies a timing regime that an unqualified “2.4×” leaves ambiguous. A reader can then
judge whether steady state matches the intended workload rather than assuming it describes cold
start as well.

## Reproduction playbook

**Proposed evaluation.** No new experiment is reported by this editorial revision.

1. First obtain the actual paper/version, public harness commit, resolved environment and raw logs. Until those artifacts exist, do not cite the draft’s numbers, commands or alleged correspondence as an empirical reproduction.

2. Define cold start and steady state separately. Give each implementation the same workload, resource limits, initialization policy and measurement window, and record tail-latency and correctness criteria before comparing throughput.

3. Archive each raw repetition with process lifetime and hardware metadata. Report variation and failures, not only the best ratio; compare cold and warm results as different questions rather than selecting the convenient winner.

## Pre-publication audit

- [ ] The real system, harness and raw outputs are available before empirical publication.
- [ ] Both implementations receive the same initialization and workload treatment.
- [ ] Every table and interactive figure is labeled illustrative until its provenance is supplied.

## Verdict

The useful lesson is a measurement contract, not a demonstrated reversal against an unnamed paper. This post is published as a hypothetical worked example, not an empirical reproduction; provenance and raw runs would be required to make that stronger claim. Do not claim an author response or corrected upstream result without a public record.
