Read a repository to identify its trust boundaries before executing its installation or examples. History, tests, dependencies, and one end-to-end request provide a useful map, not a safety certificate. Pin the source, separate documented intent from observed implementation, and postpone execution until the risks and permitted environment are explicit.

## Engineering quick-spec

| Review boundary | What this draft covers |
| --- | --- |
| Evidence level | Read-only source assessment before deciding whether to execute |
| Input contract | Pinned commit, entry point, dependency boundary and error path |
| Main limitation | Maintenance signals and visible tests can be mistaken for security or correctness proof |

## Start with the history, not the README

A Git log records changes visible in that repository’s history. It can reveal design pressure, but squashing, imported history and private work limit what it tells you; it cannot establish how hurried or careful an author was.

```bash
git log --oneline --no-merges | head -40
git shortlog -sn --no-merges | head -10
git log --since="1 year ago" --format="%ad" --date=format:"%Y-%m" | sort | uniq -c
```

Read the shape of that output. A project with one author and forty commits in the last month is a
different thing from one with nine authors and a burst of activity three years ago. Neither is bad,
but they call for different kinds of trust.

<Callout tone="tip" title="Look for the commits nobody advertises">
  Search for the unglamorous fixes: `git log --grep="fix" --grep="revert" --grep="hotfix"`. Revert
  commits tell you where the design pushed back. The absence of reverts does not establish an absence of users or failures.
</Callout>

## Three signals I read next

I look for three things, in this order, and I stop as soon as one of them fails badly.

1. **Test-to-source ratio, by directory.** File counts help locate tests, not establish their quality or coverage. Read assertions and failure cases before drawing conclusions about a subsystem.
2. **The dependency graph.** Not the count — the shape. Runtime dependencies that pull in build tools,
   or a single package that appears in every layer, are a maintenance cost you are about to inherit.
3. **Error paths.** Pick the most important public function. Read what happens when it fails. If the
   failure mode is a raised generic exception, the boundaries are probably not designed yet.

## Read one request end to end

After the three signals, I trace a single request through the code. Not a mock, not a unit test — the
actual entry point, down to whatever it writes, and back up to whatever it returns.

<Sidenote>
  This is where most "it looked clean" impressions fall apart. Layers that read well in isolation
  often pass the same dictionary through six modules under five different names.
</Sidenote>

I keep a scratch file with three columns: module, input, output. When a module's input and output are
the same object, I mark it. Those are usually either adapters or places where the design has stopped
making decisions. Both are useful to know before I depend on the project.

## What this buys you

By the time I run the install command, I already know whether the project is a maintained system or a
published snapshot, where its tests actually point, and which boundaries need testing under my workload; reading alone cannot predict the first failure.

## Reproduction playbook

**Proposed evaluation.** No new experiment is reported by this editorial revision.

1. Record the repository URL and full commit identifier. Read manifests, install scripts, contribution/security guidance and license files as text; do not enable hooks or run a build just to discover what installation does.

2. Trace one important entry point through validation, state changes and error handling. Keep a small input/output/side-effect ledger and identify which claims have a code locator versus only a README statement.

3. Choose a separate authorized execution phase only after defining isolation, credentials and expected outputs. Archive exact commands and failures if you run it; leave unexecuted tests explicitly unexecuted in the review.

## Pre-publication audit

- [ ] Install/build hooks are inspected before any decision to execute them.
- [ ] A test-file count is not reported as test coverage or a reliability score.
- [ ] Runtime and security conclusions remain bounded by actual tests performed.

## Verdict

Use source reading to choose what to test and whether a project deserves a controlled trial. Do not use contributor counts, commit tone or an attractive module graph as a verdict on safety. The best outcome may be a clear list of unresolved risks rather than an install command.
