Prithvi-EO-2.0 is a multi-temporal Earth-observation foundation model trained on global HLS imagery. Its optional time-and-location embeddings add scene metadata to image tokens. The reported 8% GEO-Bench gain compares several changes at once; matched plain/TL controls, input validation, and held-out regions are more useful deployment tests than that headline alone.

<Callout tone="warning" title="A benchmark lead is not a deployment result">
The paper reports results; this article does not report an independent training run. Architecture details below are cross-checked against pinned TerraTorch source. Task metrics and bibliographic details are attributed to the supplied manuscript and its linked paper; recheck the exact paper version and checkpoint card when reproducing them.
</Callout>

This deep dive connects token geometry, six checkpoint entries, downstream tables, and a proposed TerraTorch evaluation protocol. The protocol is an engineering starting point, not a tested installation recipe or a guarantee of GPU memory requirements.

<KeyTakeaways>

- **Temporal tokenization is decoupled from spatial patching:** Each pretraining sample contains `T = 4` frames spanning 1–6 months; 3D convolutional patch embedding uses temporal kernel size `t = 1` (preserving per-frame tokens), while factorized 3D sinusoidal positional encodings span time, height, and width.
- **Metadata is an additive bias, not an extra spectral band:** `-TL` checkpoints encode acquisition `(year, day_of_year)` and scene center `(lat, lon)` via 2D sinusoidal projections summed onto tokens with learned scalar weights and a `p = 0.1` metadata dropout rate.
- **Six checkpoints ship, but only two matched ablation pairs exist:** Hugging Face hosts `tiny-TL` (5M), `100M-TL` (100M), `300M` / `300M-TL`, and `600M` / `600M-TL`. Clean metadata ablations require pairing `300M` vs. `300M-TL` or `600M` vs. `600M-TL` on identical splits.
- **The 8% GEO-Bench headline is a confounded aggregate:** It reflects simultaneous increases in parameter count (`100M → 600M`), corpus scale (`250K` US `→ 4.2M` global), temporal horizon (`T=3 → T=4`), and metadata conditioning. Task-level tables reveal modest margins (e.g., `+0.6` Water IoU on Sen1Floods11 for `600M-TL` vs. `600M`; `+0.5` mIoU over U-TAE on PASTIS).
- **Spatial-temporal OOD testing is mandatory before deployment:** Because `(lat, lon)` and `day_of_year` are strong geographic/phenological priors, fine-tuned `-TL` models must be evaluated on held-out regions and held-out years alongside plain controls.


</KeyTakeaways>

## What does Prithvi-EO-2.0 actually add mathematically and architecturally?

Prithvi-EO-2.0 extends the VideoMAE / Spatiotemporal MAE paradigm (He et al., 2022; Tong et al., 2022; Feichtenhofer et al., 2022) to multi-spectral satellite time series with two targeted structural changes: **factorized 3D spatiotemporal tokenization** and **learned-weight sinusoidal metadata injection**.

```text
HLS cube (6 bands × T dates × H × W)
  -> Conv3D with kernel = stride = (1, patch_h, patch_w)
  -> per-axis positional encoding + optional date/location bias
  -> retain 25% visible tokens -> ViT encoder
  -> reinsert mask tokens -> lightweight decoder -> masked-pixel MSE
```

The arrows show information flow, not a measured execution profile.

### 1. 3D Patch Tokenization and Factorized 3D Positional Encoding

Given a standardized multi-temporal HLS cube `X ∈ R^(C × T × H × W)` with `C = 6` spectral channels and `T = 4` chronological frames, a single 3D convolution projects non-overlapping spatiotemporal cubes of size `(t, h, w)` into `D`-dimensional token embeddings:


```text
Z_0 = Conv3D(X; kernel=(t,h,w), stride=(t,h,w)) ∈ R^(N × D)
```


where the total token count is:


```text
N = (T / t) × (H / h) × (W / w)
```


Crucially, Prithvi-EO-2.0 sets **`t = 1`**. That means the convolution **never mixes separate acquisition months inside a single patch token**. Instead, each timestamp produces its own spatial grid of tokens (`14 × 14 = 196` tokens/frame for `h=w=16`; `16 × 16 = 256` tokens/frame for `h=w=14`), and cross-temporal interactions happen exclusively through multi-head self-attention across the full token sequence.

To inform attention layers of where each token sits inside the 3D cube, the authors generate three independent 1D sinusoidal positional encodings along time (`t`), height (`h`), and width (`w`) and concatenate them into a single vector `E_(pos) ∈ R^(N × D)`:


```text
E_(pos)(n) = [ e_(t)(n) ‖ e_(h)(n) ‖ e_(w)(n) ]
```


### 2. Optional Time-and-Location (`-TL`) Metadata Fusion

In the `-TL` checkpoints, each sample carries two auxiliary metadata tuples:

- **Temporal coordinates:** `τ_k = (year_k, DOY_k)` for each frame `k ∈ (1, …, T)`, where `DOY_k` follows the chosen implementation’s year/day convention (including its leap-year handling).
- **Spatial geolocation:** `ℓ = (lat, lon)` at the center of the patch.

Both tuples are independently mapped to `R^(D)` via fixed 2D sinusoidal encodings, `φ_(time)(τ_k)` and `φ_(loc)(ℓ)`, and fused into the token representation via **learned scalar weights** (`w_(time), w_(loc)`—with separate scalar parameters for encoder and decoder) gated by independent Bernoulli dropout masks `m_t, m_ℓ ~ Bernoulli(1 - p_(drop))` with `p_(drop) = 0.1` during pretraining:


```text
conditioned_token_n = image_token_n + positional_encoding_n
                    + time_gate × time_weight × time_encoding(frame(n))
                    + location_gate × location_weight × location_encoding(scene)
```


Two engineering consequences follow directly from this equation:

1. **Graceful degradation:** With a reported 0.1 dropout probability for each metadata source, the model is exposed to missing metadata during training; that is not a guarantee of calibrated predictions under missingness or distribution shift.
2. **Global scene context, not pixel geometry:** Every token within frame `k` receives the *same* `φ_(time)(τ_k)` and every token in the entire sample receives the *same* `φ_(loc)(ℓ)`. Metadata acts as a learned scene-level bias, not an additional spatially varying spectral channel.

### 3. Asymmetric Masked Autoencoding Objective

During pretraining, a uniform random subset `M`, a subset of patch indices 1 through N, containing `ρ = 75%` of all tokens is masked out. Only the remaining `25%` visible tokens the complementary visible set V pass through the heavy ViT encoder, yielding a fourfold reduction in encoder token count. The quadratic attention-score term shrinks by roughly sixteenfold; linear projections, MLPs and the full-token decoder have different costs, so this is not a measured end-to-end speedup. The lightweight 8-layer decoder (`D_(dec) = 512`) receives the encoded visible tokens interleaved with shared learnable `[MASK]` tokens, re-applies decoder 3D positional and `-TL` embeddings, and predicts raw reflectance pixels. The training loss computes mean squared error (MSE) strictly over masked patches (`norm_pix_loss = false`):


```text
L_MAE = mean over masked patches i of MSE(predicted_pixels_i, target_pixels_i)
```


The pretraining objective is easier to feel than to read. ### Architecture Decision Records (ADRs)

Understanding *why* the authors chose this design clarifies where the model excels and where it breaks:

- **ADR-01: Temporal Patch Size `t = 1` Instead of Spatiotemporal Tubelets (`t = 2`)**
  - *Context:* VideoMAE typically merges adjacent frames (`t=2`) because consecutive video frames at 30 fps are highly redundant.
  - *Decision:* Keep `t = 1` for HLS multi-temporal stacks.
  - *Consequence:* Satellite acquisitions are spaced 1–6 months apart; land cover changes dramatically between frames. Keeping `t = 1` removes a temporal-kernel interpolation obstacle when adapting to single-date (`T=1`) or variable-length downstream tasks; supported sequence lengths must still be checked against the selected implementation. Token count grows linearly with T, while dense attention scores grow quadratically.
- **ADR-02: Additive Learned-Weight Metadata Biases Over Extra Input Channels**
  - *Context:* Appending latitude, longitude, and DOY as extra raster channels forces downstream pipelines to construct dense metadata rasters and breaks when metadata is missing.
  - *Decision:* Encode metadata via sinusoidal embeddings scaled by learned scalars with `p = 0.1` dropout.
  - *Consequence:* Enables zero-shot fallback when timestamps or coordinates are missing, while introducing a subtle geographic-prior overfitting risk (analyzed below).
- **ADR-03: `14 × 14` Spatial Patching on the 600M Backbone**
  - *Context:* Standard ViT-Huge uses `14 × 14` patches (`224 / 14 = 16` grid), whereas ViT-Large uses `16 × 16` (`224 / 16 = 14` grid).
  - *Decision:* Retain ViT-H/14 geometry at 600M.
  - *Consequence:* Yields finer spatial token granularity (`256` vs. `196` patches per `224 × 224` frame), but breaks divisibility for standard `512 × 512` EO tiles (`512 mod 14 = 8`), forcing resizing (e.g., to `448 × 448` as done on Sen1Floods11) or explicit reflect-padding in inference pipelines.

## What exactly went into pretraining?

The sampling design is as consequential as the transformer architecture: four observations span *months*, not four adjacent days. The authors stratified global HLS tiles from 2014–2023 across land-cover types, filtered out excessive clouds and no-data pixels, and enforced geographic separation between training and validation footprints to avoid spatial leakage.

## Does the 8% GEO-Bench gain survive a peer-review audit?

The paper evaluates Prithvi-EO-2.0 on **GEO-Bench** (Lacoste et al., 2023): six classification datasets and six semantic-segmentation datasets spanning spatial resolutions from `0.1 m` to `15 m`, using 10 Bayesian hyperparameter optimization (HPO) trials per dataset (via TerraTorch Iterate) followed by 10 repeated runs with distinct random seeds. The headline result is that `Prithvi-EO-2.0-600M-TL` outperforms `Prithvi-EO-1.0` by **8%** across the benchmark and ranks first overall against six competing geospatial foundation models (`MoCo`, `DINO`, `DeCUR`, `Scale-MAE`, `DOFA`, and `Satlas`).

A strict methodological audit surfaces four caveats that every practitioner should weigh before citing that 8% number:

1. **Task-family divergence is hidden inside the aggregate:** In the paper’s own GEO-Bench breakdown (Section IV-A), **DOFA** (Xiong et al., 2024)—pretrained on multi-sensor imagery spanning NAIP, Sentinel-1, Sentinel-2, EnMAP, Gaofen, and Landsat—**ranks first on classification**, with `Prithvi-EO-2.0-600M-TL` second and `600M` third. Prithvi-EO-2.0’s overall lead is driven primarily by **semantic segmentation**, where `600M-TL` and `600M` top the leaderboard ahead of `DeCUR` and `DINO` ResNet-50 baselines.
2. **Aggregation ambiguity in the abstract:** GEO-Bench normalizes heterogeneous task metrics (accuracy, F1, mIoU) and typically aggregates via interquartile mean (IQM) with bootstrap confidence intervals (Agarwal et al., 2021). The abstract’s single "8%" figure does not distinguish absolute percentage points from relative lift or expose per-task variance; individual task tables are far more reliable decision tools.
3. **Confounded pretraining variables:** Comparing `Prithvi-EO-2.0-600M-TL` to `Prithvi-EO-1.0-100M` mixes `6×` parameter scaling, `17×` corpus expansion, global vs. CONUS geography, `T=4` vs. `T=3` temporal inputs, and `-TL` metadata.
4. **Resolution transfer works surprisingly well—with a caveat:** Strong performance on `0.1 m–15 m` tasks despite strictly `30 m` pretraining shows that ViT MAE features transfer across spatial scales, yet domain-specific multi-sensor models (e.g., SAR-native or hyperspectral models) remain competitive when spectral modalities diverge from optical HLS.

### 3. Multi-Modal Ecosystem Dynamics: Gross Primary Productivity (GPP)

In a separate flux-tower regression benchmark, the authors fused HLS imagery with MERRA-2 meteorological variables across 37 globally distributed flux towers (`975` samples) using leave-one-year-out cross-validation. `Prithvi-EO-2.0-600M-TL` achieved held-out `R^2` scores of **`0.88` (2018), `0.80` (2019), `0.83` (2020), and `0.74` (2021)**—averaging **`0.81`** versus **`0.75`** for a ResNet-18 baseline ([Table XV](https://arxiv.org/html/2412.02732#S4.T15)). Notice the inter-annual variance (`0.88 → 0.74`): temporal distribution shift remains non-trivial even with a 600M-parameter backbone.

## Where do the metadata embeddings help, and where could they hurt?

Optional metadata is smart systems engineering. Real Earth-observation pipelines routinely lose exact acquisition dates during cloud-free compositing and drop coordinate tags when tiles are shuffled into web-dataset shards. Treating time and location as droppable hints makes the model able to accept missing metadata by design; comparative resilience still requires measurement.

However, the same mechanism introduces a classic **shortcut-learning failure mode**:

- **Geographic memorization:** Center `(lat, lon)` encodes biome, climate zone, and regional agricultural policy. A fine-tuned `-TL` model can score well on an in-distribution test split by learning *"this latitude/longitude usually grows maize in July"* rather than extracting generalizable canopy reflectance signatures.
- **Phenological brittleness under climate anomalies:** When drought, late planting, or El Niño shifts a growing season by 4–6 weeks, a model over-reliant on `day_of_year` biases can misclassify healthy delayed crops or misjudge burn-scar recovery.
- **Consortium-assembled evaluation bias:** Involving remote-sensing subject-matter experts (SMEs) in benchmark curation increases operational realism, yet end-user-designed splits still predominantly test expected seasonal and regional regimes unless explicitly partitioned for out-of-distribution (OOD) generalization.

### Diagnostic Decision Tree: Should You Ship Plain or `-TL`?

1. If inference metadata is unreliable, begin with the same-sized plain control; separately test the TL checkpoint with missing metadata.
2. Freeze in-distribution, held-out-region and held-out-year splits before tuning.
3. Compare same-sized plain and TL checkpoints with identical data, decoder, seed schedule and tuning budget.
4. Prefer the variant that meets the operational error and uncertainty criteria across the required splits. An OOD win supports the deployment decision; it does not prove that metadata contains no shortcuts.
5. If TL gains disappear under shift, retain the control or investigate metadata dropout as a separately tuned experiment—not a prescribed fix.

## Step-by-Step Reproducible Engineering Playbook (TerraTorch)

The supplied manuscript reports a pretraining budget of 21K–58K A100 GPU-hours. Fine-tuning through [TerraTorch](https://github.com/IBM/terratorch) (Gomes et al., 2025) is a more accessible starting point, but single-GPU feasibility depends on the checkpoint, task, batch size and precision; it has not been tested here. The proposed workflow below has not been executed. Resolve exact dependency versions, GPU memory limits, dataset paths and CLI schema before calling it reproducible.

### Step 1: Pin Your Environment and Verify GPU Precision

Never track `main` on fast-moving geospatial toolkits; configuration schemas in TerraTorch evolve across minor releases. Pin versions explicitly and verify BF16/FP16 support:

```bash
# In the isolated environment you intend to test; no model download or training.
python --version
python -m pip freeze > environment.resolved.txt
python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available())"
```

Freeze the exact resolved TerraTorch/PyTorch/Lightning versions, CUDA driver, hardware, checkpoint revision and data-manifest hashes. A range such as `terratorch==1.0.*` is not an exact pin. Do not install an old research requirements file blindly: the [pinned upstream requirements](https://github.com/NASA-IMPACT/Prithvi-EO-2.0/blob/758311280f935d4775c05b26d792768bf1fda841/requirements.txt) describe a historical environment, not a current security recommendation.

### Step 2: Enforce the Exact HLS Band Order, Units, and Divisibility

Most silent failures in Prithvi fine-tuning come from band permutation (e.g., passing Sentinel-2 `B08` broad NIR instead of `B8A` narrow NIR, or feeding scaled `0–1` floats against `0–10000` normalization constants). The illustrative validator below checks layout and divisibility, not georegistration or band identity. Apply the nodata/cloud policy first, reject nonfinite values, and avoid double-normalization if the datamodule already scales the inputs:

```python
import numpy as np
import torch

# Exact pretraining statistics from ibm-nasa-geospatial/Prithvi-EO-2.0-600M-TL config.json
# Band order: [Blue, Green, Red, Narrow NIR, SWIR 1, SWIR 2]
HLS_MEAN = torch.tensor([1087.0, 1342.0, 1433.0, 2734.0, 1958.0, 1363.0]).view(1, 6, 1, 1, 1)
HLS_STD  = torch.tensor([2248.0, 2179.0, 2178.0, 1850.0, 1242.0, 1049.0]).view(1, 6, 1, 1, 1)

def prepare_hls_cube(raw_cube: np.ndarray, patch_size: int = 14) -> torch.Tensor:
    """
    raw_cube: shape (C=6, T, H, W) in HLS reflectance * 10_000 units (int16/float32).
    Validates channel count and spatial divisibility by backbone patch_size.
    """
    assert raw_cube.ndim == 4 and raw_cube.shape[0] == 6, f"Expected (6, T, H, W), got {raw_cube.shape}"
    assert np.isfinite(raw_cube).all(), "Handle nonfinite pixels before normalization"
    _, t, h, w = raw_cube.shape
    assert t > 0 and h > 0 and w > 0 and patch_size > 0
    assert h % patch_size == 0 and w % patch_size == 0, (
        f"Spatial dims ({h}, {w}) must be divisible by patch_size={patch_size} "
        f"(e.g., 224 or 448 for 600M ViT-H/14)."
    )
    assert not (raw_cube == -9999).any(), "Apply the dataset-specific nodata policy first"
    x = torch.from_numpy(np.ascontiguousarray(raw_cube)).float().unsqueeze(0)  # (1, 6, T, H, W)
    return (x - HLS_MEAN) / HLS_STD

# Model loading is deliberately omitted: do not allocate two 600M models
# merely to check input layout. Test one pinned backbone at a time in eval()
# under torch.inference_mode(), with real aligned metadata and finite outputs.
```

### Step 4: Configure a Matched Plain vs. `-TL` Fine-Tuning Experiment in TerraTorch

Below is an unexecuted, version-dependent TerraTorch semantic-segmentation model/trainer sketch (not a complete configuration: the data module and split manifests are intentionally absent) (patterned after Sen1Floods11 / multi-temporal HLS segmentation). To run a strict ablation, hold **every single line constant**—including `seed_everything`, split manifests, learning rate, and decoder—and toggle only `backbone` (`prithvi_eo_v2_300` vs. `prithvi_eo_v2_300_tl`) and `coords_encoding`.

```yaml
# configs/prithvi_v2_ablation_template.yaml
seed_everything: 42
trainer:
  accelerator: gpu
  devices: 1
  precision: bf16-mixed
  max_epochs: 50
  gradient_clip_val: 1.0
  callbacks:
    - class_path: lightning.pytorch.callbacks.ModelCheckpoint
      init_args:
        monitor: val/Multiclass_Jaccard_Index
        mode: max
        save_top_k: 1
    - class_path: lightning.pytorch.callbacks.EarlyStopping
      init_args:
        monitor: val/Multiclass_Jaccard_Index
        patience: 10
        mode: max

model:
  class_path: terratorch.tasks.SemanticSegmentationTask
  init_args:
    model_factory: EncoderDecoderFactory
    model_args:
      # Swap to "prithvi_eo_v2_300" (and remove coords_encoding) for matched plain control
      backbone: prithvi_eo_v2_300_tl
      backbone_pretrained: true
      backbone_num_frames: 4
      backbone_bands: [BLUE, GREEN, RED, NIR_NARROW, SWIR_1, SWIR_2]
      backbone_coords_encoding: [time, location]
      necks:
        - name: SelectIndices
          indices: [5, 11, 17, 23]   # For 600M (depth=32), use [7, 15, 23, 31]
        - name: ReshapeTokensToImage
          effective_time_dim: 4
        - name: LearnedInterpolateToPyramidal
      decoder: UNetDecoder
      decoder_channels: [512, 256, 128, 64]
      head_dropout: 0.1
      num_classes: 2
    loss: ce
    ignore_index: -1
    freeze_backbone: false
    optimizer: AdamW
    lr: 1.0e-4
    scheduler: CosineAnnealingLR
    scheduler_hparams:
      T_max: 50
      eta_min: 1.0e-6
```

After resolving and validating the missing data configuration, run both the plain and TL variants across the same fixed seeds (or automate 10 HPO trials + 10 seeds using `terratorch-iterate`) and log both **in-distribution test metrics** and **spatial/temporal OOD holdout metrics**:

```text
for variant in [300M_plain, 300M_TL]:
    for seed in [42, 1337, 2026]:
        validate resolved config and frozen split hashes
        fit on training data; select using validation data only
        evaluate once on in-distribution and frozen OOD test splits
        archive config, checkpoint, raw predictions, seed and resource measurements
```

The exact keys and metric names depend on the pinned toolkit version. In particular, compare with the [official Sen1Floods11 configuration](https://github.com/NASA-IMPACT/Prithvi-EO-2.0/blob/758311280f935d4775c05b26d792768bf1fda841/configs/sen1floods11.yaml), which includes a data module and uses 224-pixel resizing in this repository snapshot. The manuscript’s paper-table discussion of 448 pixels is a different experimental configuration, not a property of that YAML file.

### Recommended Order of Evaluation Benchmarks

If you are validating Prithvi-EO-2.0 for a production EO stack, sequence your experiments from cheapest to most diagnostic:

1. **Sen1Floods11 (Single-date binary segmentation):** Small (`446` tiles), public, and a candidate for a small first experiment; runtime depends on the hardware and configuration. Validates band handling, normalization, and patch-size resizing (`448 × 448`).
2. **HLS Burn Scars (Single/multi-temporal HLS domain match):** Closest to the pretraining sensor and radiometry; the NASA-IMPACT repository ships working reference configs.
3. **PASTIS or US Multi-Temporal Crop Segmentation:** Directly tests temporal attention and phenology—the single best arena for a matched `300M` vs. `300M-TL` ablation with a held-out geographic fold and held-out year.
4. **BioMassters or Landslide4Sense:** Stress-tests continuous regression (above-ground biomass) or multi-sensor fusion (Sentinel-1 SAR + Sentinel-2 optical), revealing where a 6-band optical MAE hits its modality ceiling.

## Pre-Deployment Audit Checklist

Before pointing Prithvi-EO-2.0 at operational satellite imagery, verify every item below:

- [ ] **Band order & radiometric units:** Confirm six reflectance bands in strict model-card order (`Blue`, `Green`, `Red`, `Narrow NIR [B8A/B05]`, `SWIR 1`, `SWIR 2`), scaled identically to the checkpoint’s `mean`/`std` config (`0–10000` reflectance scale).
- [ ] **Patch-size divisibility:** Verify `config.json` for your exact checkpoint (`16` vs. `14`). For `600M` / `600M-TL` (`14 × 14` patches), use tiled sliding-window inference with window sizes divisible by 14 (e.g., `224 × 224` or `448 × 448`) and overlap blending.
- [ ] **Chronological frame ordering:** Keep multi-temporal frames strictly sorted oldest-to-newest and co-registered to the exact same geographic footprint.
- [ ] **Matched metadata ablation:** Never compare `100M-TL` to `300M` and attribute the delta to metadata. Pair `300M` vs. `300M-TL` or `600M` vs. `600M-TL` on frozen spatial and temporal OOD splits.
- [ ] **NoData & cloud masking policy:** Confirm how masked/cloud fill values (e.g., `-9999` in HLS) are handled prior to standardization so extreme negative sentinels do not explode layer-norm statistics.
- [ ] **License compliance:** Verify MIT (NASA-IMPACT repo) vs. Apache-2.0 (TerraTorch & Hugging Face weight cards) for every artifact bundled into your container.
- [ ] **Reconstruction sanity check:** Run `inference.py` on a known AOI scene before interpreting downstream task metrics.

## Verdict: What does this release get right—and what remains hidden?

**What it gets right:** Prithvi-EO-2.0 sets a high bar for inspectability in geospatial AI. Public Apache-2.0 weights across six checkpoints, matched plain/`-TL` ablation pairs at 300M and 600M, native TerraTorch integration, explicit multi-seed GEO-Bench protocols, and transparent task-level tables make it unusually straightforward to audit and fine-tune on a single GPU.

**What it hides:** Two gaps remain. First, the supplied sources do not include the exact **4.2M-patch pretraining manifest**—released configurations provide a starting point for downstream reproduction, but you cannot audit potential geographic overlap between the pretraining corpus and arbitrary downstream test regions without recreating the HLS sampling pipeline. Second, the headline **8% GEO-Bench figure** compresses distinct classification and segmentation behaviors (and a `6×` model + `17×` data scale-up) into a single number. Treat Prithvi-EO-2.0 as a strong, well-engineered multi-temporal optical backbone—then let your own matched plain vs. `-TL` OOD experiment decide whether it earns a slot in production.
