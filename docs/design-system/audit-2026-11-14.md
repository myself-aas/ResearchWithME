# Design-system audit — reme / ResearchWithMe

**Date:** 2026-11-14  
**Branch:** `arena/7c1641ff-researchwithme`  
**Type:** repository-wide source audit and design critique; recommendations, not implementation.

## Verdict

**The editorial direction fits the product; system conformance is not yet reliable.** Keep the scholarly identity, but fix the token contract before extending the component library. A reproducible token build and passing base contrast checks currently coexist with undefined component variables, frozen light-theme aliases, and low-contrast domain text.

This is not a reason to replace reme with a generic SaaS kit. The strongest product-specific assets are citation-first reading, source/provenance details, explicit research states, and a quiet long-form reading measure. They should carry more of the identity than repeated decorative labels or animation.

## Pass 1 — Compact design intent

This is a proposed clarification of existing decisions, **not authorization to change the normative spec**.

### Product and audience

An open research reading and review platform for researchers, graduate scholars, reviewers, and independent investigators. The primary job is to find a review, understand its claim, inspect its source, and reuse it with attribution. Studio controls support that work; they should not dictate the reader's visual language.

### Base palette: retain the current implemented light values

| Name | Value | Role |
|---|---|---|
| Archival paper | `#FAF9F6` | Reading canvas |
| Folio surface | `#F3F1EC` | Quiet grouped controls and panels |
| Ink | `#121214` | Main text |
| Secondary ink | `#5C5C63` | Supporting text |
| Reference blue | `#1D4ED8` | Links, focus, primary actions |
| Replication green | `#047857` | Defined positive research/success roles, with text labels |

Dark mode remains the existing Obsidian semantic map, not an inverted approximation. Caution, contradiction, and provenance need separate foreground/background/border roles; one domain hex should not serve every contrast purpose.

### Typography

Honor the explicit Aptos direction: Aptos Serif for editorial content, Aptos for interface controls, Aptos Mono for identifiers/code, all requested by installed name only. Preserve bundled Newsreader/Inter as reliable fallbacks. Use serif headlines and reading text as intentional scholarship cues, not decorative contrast. Reserve mono for literal data, code, DOI, and citation syntax rather than all small labels. Keep reading text at approximately 18px/1.7 and ≤68ch unless the approved spec changes.

### Layout alternatives and alignment

**A — Preferred: evidence-led editorial index.** Left-aligned masthead/search followed quickly by a real review with a visible source trail; facts remain adjacent to the work.

```text
Masthead                       Search / account
Review headline and short purpose
Search / compact topic + format controls
Lead review                    Source / author / method
Review index                   Optional context
```

**B — Retain current broad introduction, but compress it.** Left-aligned introduction and summary rail remain, while reducing pre-result height and duplicate orientation copy.

```text
Introduction + search          Small archive summary
Compact filters
Featured review
Index
```

For articles, keep left-aligned reading with a quiet metadata/citation rail on wide screens and progressive disclosure on phones. Do not justify body copy or force desktop columns onto phones. Centered alignment belongs to genuinely isolated states, not long technical text.

### Principles

- Make provenance, not decoration, the memorable element.
- Borders separate meaningful groups; do not box every paragraph.
- Research labels name evidence status, not aesthetic status.
- Preserve useful metadata; reduce duplicate labels before reducing information.
- A save, filter, or citation interaction may animate; reading does not need recurring choreography.

## Pass 2 — Review against the brief

The skill flags cream canvases, serif display, hairline rules, monospace metadata, and uppercase eyebrows as common defaults. Here, **the brief explicitly asks for an archival scholarly direction**, so automatically replacing cream/serif would be the wrong application of the skill.

Revision to the initial direction: keep paper, serif, and useful rules, but remove the assumption that every heading needs an eyebrow, every metadata fragment needs mono/all-caps, or every section needs entrance motion. Spend distinctiveness on an inspectable source trail. This preserves the commissioned identity while reducing template-like chrome.

No code changes follow from this plan in this audit.

## Findings

Priority: **P1** contract/accessibility blocker; **P2** significant consistency/maintenance issue; **P3** refinement or adoption guidance. Exposure is called out where components are not currently route-integrated.

### DS-01 · P1 · Generated component CSS names do not match consumers

**Evidence:** `tokens/scripts/build.mjs:72` calls:

```js
cssVars({ component: resolved.component }, 'component')
```

Both the wrapper key and prefix contribute `component`, emitting names such as:

```css
--reme-component-component-source-card-background: #F3F1EC;
```

But `lib/scholarly/source-card.ts:35–39` requests `--reme-component-source-card-background`, without the duplicate segment. The same mismatch affects `lib/scholarly/evidence-card.ts:85–89` and `lib/scholarly/claim-card.ts:23–27`.

**Result:** 15 unique requested component variables are absent from the generated CSS. The corresponding declarations cannot apply their intended values. Depending on property and other styles, the browser falls back to inheritance/initial behavior rather than the intended component recipe.

**Exposure:** Source/Evidence/Claim reference components and future consumers; do not infer that every existing article card is affected.

**Fix:** emit one canonical prefix, regenerate outputs, and verify all CSS-variable consumers resolve. Add a test of emitted names, not only JSON references or markup strings. Do not manually patch generated CSS.

**Acceptance:** zero unresolved `--reme-*` consumers across both runtime source trees, and computed card backgrounds/borders/text match approved recipes in a browser.

### DS-02 · P1 · Component color aliases are permanently light-theme literals

**Evidence:** `tokens/src/component.json` references `semantic.light.*`. The generator resolves the tree to literals before CSS emission and only overrides semantic colors under dark selectors (`tokens/scripts/build.mjs:65–84`). Component aliases receive no equivalent dark overrides.

**Impact:** simply repairing DS-01 activates light backgrounds/text inside dark mode. This is a second defect, not a duplicate of the naming issue. TypeScript component exports are also light-resolved, so non-CSS consumers need an explicit theme contract.

**Fix:** emit runtime CSS aliases such as `var(--reme-surface)` for component color roles, or generate complete theme-specific component maps. Keep non-color fixed values separate. Avoid using resolved light constants for a runtime-themed interface.

**Acceptance:** each reference component renders correctly in explicit light, explicit dark, and system mode, including hover/selected/error states. Compare computed values before and after a theme change.

### DS-03 · P1 · Domain foreground colors fail normal-text contrast

**Evidence:** `components/primitives/Badge.tsx:8–10` uses domain tokens as small text plus a 10% tint of the same color. Additional calculations from `tokens/src/semantic-light.json`:

| Foreground / surface | Contrast | Normal text target |
|---|---:|---:|
| `trust.emerging` `#0891B2` on surface `#F3F1EC` | 3.26:1 | 4.5:1 |
| `trust.uncertain` `#D97706` on surface | 2.82:1 | 4.5:1 |
| Emerging on its 10%-tinted surface | 2.92:1 | 4.5:1 |
| Uncertain on its 10%-tinted surface | 2.56:1 | 4.5:1 |

Tint calculations use ordinary sRGB alpha compositing over `surface`. Actual ratios depend on the parent surface, so rendered validation must cover other placements too. Dark emerging/uncertain values pass these specific calculations.

**Fix:** define domain foreground, subtle background, and border roles independently. Darken light-theme text roles or use neutral text with a meaningful colored marker. Expand tests to every supported Badge variant and actual surface. A darker foreground token must still express the same state.

**Important:** `tokens:check` does not currently test these pairs; its pass is not contradictory. The same cyan/amber values occur in other domain maps, so audit their text usage before treating those maps as safe.

### DS-04 · P1 · There is no unambiguous current specification

**Evidence:**

- `DESIGN.md` declares the full `docs/reme-design-system-v3.1.md` normative.
- That spec's front matter still gives primary `#4F46E5`, canvas `#F8F7F3`, emerald verification, and a 72ch reading style.
- `tokens/src/semantic-light.json`, `DESIGN.md` machine-readable values, and runtime CSS use primary `#1D4ED8`, canvas `#FAF9F6`, blue verification, and a 68ch reading measure.
- `.impeccable/surfaces/app-page-tsx.md` still calls for amber actions/emerald verification and “No kickers above headings,” while `BlogHero` starts with an eyebrow.
- `tokens/src/primitive.json` still names the old fallback font families; runtime CSS leads with Aptos. The full spec has a later Aptos note but its machine-readable family block remains different.
- `app/globals.css` says its breakpoints match `tokens/src/layout.json`; the actual source is `primitive.json → layout`.

**Impact:** a developer can follow the stated source of truth and regress the implemented system. Existing documents cannot all be treated as current instructions.

**Fix:** approve a single versioned decision, reconcile normative front matter/prose, generate reference tables from tokens, and mark historical inventories as dated snapshots. Do not silently choose a new palette during cleanup.

### DS-05 · P2 · Typography has parallel scales rather than one governed scale

**Evidence:** `components/primitives/Text.tsx:38–56` offers legacy “house” patterns alongside spec patterns. `page-title` uses 24/30px bold, while `title-1` uses fluid 32–48px at weight 500. The hero adds another 36/48/60px bold recipe (`components/BlogHero.tsx:57–62`); article titles use their own recipe. Both scales may be useful, but semantic naming does not explain which page uses which.

The primitive also uppercases `label`, `eyebrow`, Badge, and Button by default. Source counts: **61 `uppercase` occurrences** across app/components TSX. This is an inventory signal, not 61 confirmed design defects.

**Fix:** publish editorial display, page title, section title, UI heading, body, metadata, and identifier recipes with explicit contexts. Distinguish heading semantics from visual size. Prefer sentence-case control labels; keep uppercase only where it intentionally serves compact archival indexing. Deprecate redundant variants through a migration map rather than changing all pages at once.

**Acceptance:** a specimen shows every role at mobile/desktop sizes in both actual fallback and Aptos environments, including italic scientific names, long titles, numeric tables, and code.

### DS-06 · P2 · Primitive sizing and override contracts disagree

**Evidence:** `Card` maps padding `lg` to `p-5`, `Box` maps `lg` to `p-6`; `Card` uses `xl=p-6`, `Box` uses `xl=p-8`. Button recipes use `rounded-sm` while component button tokens specify `radius.md`. `Icon` provides five size keys while primitive tokens describe three sizes and a 1.75px stroke; the wrapper does not apply that stroke token.

`components/primitives/cx.ts` deliberately concatenates without conflict resolution. `Text` nevertheless allows `weight` and `className` alongside variant weight classes. For example, a bold `page-title` plus `weight="normal"` emits both classes. HTML class order alone does not guarantee the intended winner.

**Fix:** choose either cross-component density/spacing semantics or clearly component-specific names. Make variants emit nonconflicting classes by construction; define whether `className` is additive-only and test supported overrides. A global merge dependency is not required to solve this.

### DS-07 · P2 · CSS specificity patches undermine token/component predictability

**Evidence:** `app/globals.css:400–455` globally enlarges tiny text classes, changes `py-0.5`/`px-1.5`, forces placeholder color with `!important`, and infers dark-surface behavior from class-name substrings. Similar rules are duplicated in Pages CSS.

**Impact:** a badge/control's apparent recipe is not its actual recipe. Patching a Tailwind utility affects unrelated consumers; substring selectors know styling syntax rather than surface semantics. Placeholder overrides bypass normal theme roles.

**Fix:** move minimum typography, control hit areas, and badge padding into component recipes; use explicit surface/placeholder roles. Remove patches incrementally with rendered regression tests. Do not simply delete them before migrating the elements they protect.

### DS-08 · P2 · Motion token governance is duplicated and visual emphasis is over-distributed

**Evidence:** `tokens/src/motion.json` owns duration/easing data, but `lib/motion/tokens.ts` manually redeclares those numbers instead of deriving them from generated output. Components contain **43 literal numeric `duration:` properties**; some match approved durations, others do not. This count is a maintenance indicator, not a blanket motion failure.

`BlogHero` stages several elements; global CSS animates main; reusable Reveal/Stagger and card hover effects add further emphasis. The implementation has good reduced-motion and SSR-safety mechanisms, but the overall motion density needs visual review.

**Fix:** parse/adapt generated motion data in one typed module, give approved exceptions names, and retain immediate state correctness independent of animation completion. Let filtering, saving, and citation disclosure own motion; remove decorative section reveals before adding new sequences. Verify full/reduced/static behavior in the browser, not just source snapshots.

### DS-09 · P2 · Theme switching lacks a complete system-mode contract

**Evidence:** `components/ThemeToggle.tsx:26–51` resolves system preference on mount and toggles only light/dark. It does not subscribe to system preference changes or offer a path back to System. Generated CSS responds to system dark unless `.light` is present, while the component may retain an earlier `.dark` class/effective state.

**Impact:** changing OS theme during a session can leave CSS, icon/label, and explicit class state inconsistent.

**Fix:** use a single persisted `light | dark | system` preference, a media-query change listener when System is selected, and one shared document-theme resolver. Test first paint, hydration, unavailable storage, and live OS changes. Preserve the early theme-init script to prevent flash.

### DS-10 · P2 · Cross-runtime and cross-channel styling still drifts

- `app/globals.css` and `cloudflare-pages/src/globals.css` duplicate most theme/base rules. Extract a common stylesheet with runtime-specific font/source setup.
- Pages image compatibility drops the custom loader and does not generate responsive candidates (`cloudflare-pages/src/compat/image.tsx`); this changes image delivery behavior across otherwise shared cards.
- `emails/_layout.tsx:26–42` hardcodes the prior indigo/green/parchment palette and fallback font stacks. Email needs literal styles and client-safe fonts, but those literals can be generated from an approved email theme instead of manually copying an old web theme.
- Generated video typography derives from `primitive.typography`, which differs from the live Aptos-first web stacks. Document whether this is an intentional rendering constraint; do not call it identical branding without that qualification.

**Fix:** one approved brand source with explicit web/email/video adapters and documented exceptions. Do not force CSS variables or unsupported custom fonts into email clients.

### DS-11 · P2 · Conformance gates test token presence more than rendered behavior

**Evidence:** `lib/__tests__/design-token-usage.test.ts` explicitly skips arbitrary values, which is where the unresolved component variables live; its scan excludes Pages. `tokens/scripts/validate.mjs` checks selected theme keys but not all nested semantic paths or consumer CSS. `scripts/release-gate.mjs` DS-4 checks scholarly components for raw hex, not resolved styles, and A11Y-1 checks that an axe suite exists. `docs/design-system/release-manifest.json` is a recorded machine-check pass with human sign-off still required—not evidence of visual correctness.

**Fix:** add consumer-to-declaration checks, recursive theme-map comparison, compiled CSS smoke tests, and browser computed-style/contrast assertions. Keep static checks, but label their scope accurately. Run browser suites for both Next and Pages; existing Playwright configuration targets Pages. Add actual viewport screenshot baselines rather than describing markup snapshots as pixel regression tests.

### DS-12 · P3 · Brand hierarchy and page density need a deliberate visual review

**Evidence:** the masthead renders `𝜋eme` (`components/BrandLogo.tsx`) while metadata, page titles, emails, and accessible home label say ResearchWithMe. This may be intentional but needs documented naming/lockup rules. Hero summary, filters, featured badge, and product placements create several pre-reading orientation layers; current route briefs also preserve some of those choices deliberately.

**Recommendation:** document the relationship between reme and ResearchWithMe, use a stable accessible brand name, and measure time/scroll distance to the first useful review on phones. Reduce duplicate orientation copy before reducing scholarly facts. Do not remove the product links or summary rail merely because they resemble a template; test their hierarchy against the actual reading task.

## What should stay

- Serif editorial reading and the 68ch implementation measure.
- Quiet archival canvas and a dark mode with independent semantic values.
- Real research metadata, citation disclosure, and explicit integrity/trust labels.
- Source/Evidence/Claim component separation and independent trust dimensions rather than a fabricated aggregate score.
- Token generation, local fonts, focus styles, reduced-motion infrastructure, and existing unit/source gates.
- Responsive 1/2/3-column article and author grids; do not increase phone density just to show more items.

## Implementation sequence and acceptance criteria

### Phase 1 — Restore contract integrity

1. Fix component variable naming and theme-aware aliasing together.
2. Add regression tests reproducing all 15 missing consumer names.
3. Introduce contrast-safe domain foreground recipes and test actual badge compositions.
4. Approve and reconcile one current normative specification; preserve historical documents as history.

**Exit:** deterministic output, zero unresolved variables, recursively complete theme maps, contrast-safe supported text/surface combinations, and correct reference-card computed styles in both themes.

### Phase 2 — Consolidate recipes

1. Align typography contexts, control labels, density, spacing, icon stroke, and radius contracts.
2. Move global utility patches into components without regressing protected text/hit areas.
3. Derive motion adapter values from generated data; complete System theme behavior.
4. Share web CSS and declare email/video adaptations.

**Exit:** a live specimen covers all primitives and states; docs examples match real component behavior; no conflicting utility output for supported prop combinations.

### Phase 3 — Evaluate composition and identity

Review home, article, author, assistant, citations/bookmarks, pricing, login/account, dashboard/editor, reference pages, and error/loading states at 320/375/768/1024/1440px, both themes, short landscape, enlarged text, keyboard-only use, and all motion modes. Include overlay-open and failed-request states. Use screenshots to decide what to remove, not to justify a preselected redesign.

**Exit:** each page has one clear primary task, a consistent title/metadata hierarchy, unobscured focus, and source/provenance information that survives reflow and printing. Link browser traces/screenshots and human sign-off to a commit-specific release manifest.

## Final recommendation

**Fix the system before embellishing the surfaces.** The largest design debt is not an insufficiently distinctive color palette; it is the gap between documented intent, generated tokens, and component behavior. Resolve that gap, then make the existing scholarly identity more recognizable through evidence-first composition and less repetitive chrome.
